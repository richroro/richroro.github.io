# 공용 보드 붙이기

기본은 서버 없이 도는 앱이다. 이 문서는 **같은 동네 사람들이 같은 속보를 보게** 할 때만 필요하다.
`config.js` 를 비워 두면 아무것도 안 바뀐다 — 지금처럼 브라우저에만 쌓이고 링크로만 오간다.

| | 서버 없이 | 공용 보드 |
| --- | --- | --- |
| 누가 씁니까 | 이미 아는 사람들(단톡방) | 같은 동네 사람들 |
| 새로 온 사람이 보는 것 | 빈 화면 (묶음 링크를 받아야 함) | 동네 속보가 바로 |
| 필요한 것 | 없음 | 아래 30분 |
| 비용 | 0원 | 무료 티어로 시작, 커지면 월 $25 |

## 1. Supabase 프로젝트 (10분)

1. [supabase.com](https://supabase.com) → New project. 지역은 **Northeast Asia (Seoul)** 로.
2. **Database → Extensions** 에서 `pg_cron` 을 켠다. (4번 파일이 쓴다)
3. **SQL Editor** 에서 순서대로 붙여 넣고 실행:
   1. `server/schema.sql` — 표 네 개
   2. `server/policies.sql` — 권한. **이걸 빼먹으면 아무나 아무 글이나 지울 수 있다**
   3. `server/seed-hoods.sql` — 동네. 열 동네만 `active = true`
   4. `server/retention.sql` — 1년 지난 리포트를 매일 지운다. **처리방침 4조가 이걸 약속한다 — 빼먹으면 방침이 거짓이 된다**
4. **Settings → API** 에서 두 값을 복사해 `config.js` 에 넣는다.

```js
window.TPW_CONFIG = {
  url: "https://xxxxxxxx.supabase.co",
  anonKey: "eyJhbGciOi...",
  hood: "4117110100"      // 기본 동네. 비우면 사용자가 고른다
};
```

> **anonKey 는 공개해도 되는 값이다.** 정적 사이트라 어차피 브라우저에 그대로 실린다.
> 이 키로 할 수 있는 일은 `policies.sql` 이 정한 것뿐이다 — 읽기는 누구나, 쓰기는 로그인한 사람이 자기 것만.
> **절대 넣으면 안 되는 건 `service_role` 키다.** 그건 모든 정책을 무시한다.

## 2. 로그인 (15분)

읽기는 로그인 없이 된다. **쓰기와 신고에만** 필요하다 — 누가 썼는지 남아야 신고가 뜻을 갖는다.

**카카오** — [developers.kakao.com](https://developers.kakao.com) 에서 앱을 만들고,
Supabase **Authentication → Providers → Kakao** 에 REST API 키와 Client Secret 을 넣는다.
카카오 쪽 Redirect URI 에는 Supabase 가 알려 주는 주소(`https://xxxx.supabase.co/auth/v1/callback`)를 넣는다.

카카오 **동의항목은 최소로** 둔다. 이 앱이 쓰는 건 "누구인지"뿐이다 — 이름은 특파원 탭에서 따로 받는다.
**실제로 켠 항목을 `privacy.html` 2조의 노란 칸에 그대로 적는다.** 방침과 설정이 어긋나면 방침이 거짓이 된다.
카카오 앱 설정의 개인정보처리방침 주소에는 `https://richroro.github.io/correspondent/privacy.html` 을 넣는다.

**메일** — 카카오 심사를 기다리는 동안 쓰는 길. Supabase 는 기본으로 켜져 있다.
앱의 `🏘 공용 보드` 시트에서 메일 주소를 넣으면 링크가 온다.

**Authentication → URL Configuration** 의 Redirect URLs 에 배포 주소를 넣어야 로그인하고 돌아온다.

```
https://richroro.github.io/correspondent/
http://127.0.0.1:8080/correspondent/     ← 로컬에서 시험할 때
```

## 3. 개인정보처리방침 채우기 (10분)

`privacy.html` 은 앱이 실제로 하는 일에 맞춰 쓴 **초안**이다. 운영자만 아는 사실이 노란 칸으로 비어 있다.

1. 운영자 이름, 개인정보 보호책임자 이름과 연락처 (14조)
2. 카카오 동의항목에서 실제로 켠 항목 (2조)
3. Supabase 프로젝트 지역(Settings → General)과 요금제의 백업 보관 기간 (4조, 8조)
4. 시행일 (16조)
5. 다 채웠으면 맨 위 `<div class="draft" id="draftNote">` 상자를 지운다

게시 전에 개인정보 전문가의 검토를 받는다. 이 문서는 법률 자문이 아니다.

## 서버가 막는 것 (실제로 돌려서 확인한 것들)

`policies.sql` 은 클라이언트를 믿지 않는다. 아래는 전부 로컬 Postgres 16 에서 공격해 보고 확인했다.

| 해 본 것 | 결과 |
| --- | --- |
| 남의 이름으로 글 쓰기 | `author` 와 `by_name` 을 토큰 주인으로 덮어쓴다 |
| 남의 리포트 id 로 덮어쓰기 | 기본키 충돌로 거부 |
| 남의 글 지우기 | 0건 삭제 |
| 남의 글 고치기 | `update` 권한 자체가 없다 |
| 로그인 없이 쓰기 | 거부 (읽기는 됨) |
| 시각을 미래로 밀어 맨 위 차지하기 | 서버가 `now()` 로 당긴다 |
| 범위 밖 값 (`wait=999`) | check 제약으로 거부 |
| 자기 글 신고해서 가리기 | 거부 |
| 같은 글 두 번 신고 | 기본키로 한 번만 |
| 정지된 사람이 자기 정지 풀기 | 프로필 표에 직접 쓸 권한이 없다. 이름·동네는 `save_profile()` 로만 바꾸고, 그 함수는 정지 기록을 안 건드린다 |
| 남의 이름으로 신고하기 | 신고자를 토큰 주인으로 덮어쓴다 |
| 도배 (25건 연속) | 시간당 20건에서 끊긴다. 하루 60건 |
| 로그인 없이 계정 삭제 함수 부르기 | 실행 권한 없음 |
| 남의 계정 지우기 | 함수는 토큰 주인의 것만 지운다. `auth.users` 직접 삭제는 권한 없음 |
| 탈퇴한 계정의 살아 있는 토큰으로 쓰기 | 프로필이 없어 거부, 프로필 재생성은 외래키로 거부 |
| 1년 지난 글 지우기를 사용자가 부르기 | 실행 권한 없음 (스케줄러만) |
| 신고로 가려진 내 글을 내가 지우기 | **된다** (처음엔 0건 삭제로 남았다 — 아래) |

`test-account.sql` 에 계정 삭제 쪽 10가지가 따로 있다. 준호가 탈퇴하면 계정·프로필·리포트·신고가 다 사라지고,
준호가 남의 글에 한 신고가 빠지면서 그 글의 신고 수가 다시 세어진다 — 3 → 2. **가림은 풀지 않는다.**
한 번 가려진 글을 되살리는 건 사람이 보고 정할 일이다.

> **처음엔 가려진 글을 쓴 사람도 못 지웠다.** Postgres 는 `DELETE ... WHERE` 에도 읽기 정책을 함께 건다.
> 읽기 정책이 `not hidden` 이라 가려진 행은 작성자에게도 안 보였고, 삭제는 0건으로 조용히 끝났다.
> 잘못 신고당한 사람이 자기 글을 치울 길이 없었다. 작성자에게는 자기 글이 보이는 정책(`reports_read_own`)을 더했다.

> **정책만으로는 못 막는 게 하나 있다.** `WITH CHECK` 안에서 컬럼 이름은 *새 행*을 가리켜서
> `banned_until = banned_until` 같은 비교는 늘 참이다. 처음엔 컬럼 권한(`update (name, hood_code)`)으로
> 막았는데, 그러면 PostgREST 의 upsert 가 떨어진다 — upsert 는 `SET` 에 보낸 컬럼을 전부 넣고 `id` 도
> 들어가서, **프로필을 처음 만들 때부터** 권한 거부가 난다. 그래서 프로필 쓰기를 `save_profile()` 함수 하나로 모았다.
>
> 이 둘(업서트, 그리고 신고의 빈 `reporter`)은 모의 서버가 가리고 있었다. 모의 서버가 SQL 을 손으로 써서
> `id` 를 빼고, 신고자를 토큰에서 채워 넣었기 때문이다. 지금 모의 서버는 **앱이 보낸 값을 그대로** 넣고,
> 커밋된 옛 정책에 PostgREST 가 만들 SQL 을 그대로 던져 두 실패를 재현한 뒤 고쳤다.

**세 사람이 신고하면 가려진다.** 지우지는 않는다. 관리자가 보고 판단할 수 있어야 한다.

```sql
-- 신고 쌓인 것 보기
select r.id, r.place, r.by_name, r.flag_count, r.hidden,
       (select array_agg(reason) from flags where report_id = r.id) as 사유
  from reports r where r.flag_count > 0 order by r.flag_count desc;

-- 오해였으면 되살리기
update reports set hidden = false where id = '...';

-- 악성 사용자 일주일 정지
update correspondents set banned_until = now() + interval '7 days' where id = '...';
```

## 위치를 받지 않는 이유

동네는 **사람이 고른다.** GPS 를 쓰지 않는다. 기술적으로 못 해서가 아니다.

좌표를 받아서 "내 주변"을 하는 순간 **위치정보법상 위치기반서비스사업 신고** 대상이 된다
(방송통신위원회). 자주 놓치는 항목이고, 1인 개발자에게는 신고 자체보다 그 뒤에 붙는
관리 의무가 부담이다. 동네를 직접 고르게 하면 이 줄을 아예 안 넘는다.

나중에 "내 주변"이 꼭 필요해지면 그때 신고하고 붙이면 된다. **순서가 그쪽이다.**

## 삭제는 어디까지 닿나

| 사본이 있는 곳 | 계정·글을 지우면 |
| --- | --- |
| 서버 | 바로 지워진다 |
| 내 기기 | 내가 쓴 글과 이름을 지운다. 남에게 받은 글은 남는다 |
| 공용 보드로 받아 간 이웃 기기 | **다음에 받아올 때 빠진다.** 받아온 범위 안에서 서버에 없는 글을 이 기기에서도 뺀다 |
| 링크로 받아 간 대화방·기기 | **회수할 수 없다.** 링크 안에 내용이 통째로 실려 있다 |

마지막 줄은 기술로 해결되지 않는다. 그래서 삭제 화면과 처리방침 7조에 그대로 적었다.

같은 규칙이 신고에도 적용된다. 세 사람이 신고해서 가려진 글은 이미 받아 간 이웃 기기에서도 다음 받아오기 때 빠진다.

## 런칭 전에 확인할 것 — 법률 자문이 아니다

- **개인정보처리방침** — `privacy.html` 초안이 있다. 3단계대로 채우고 검토를 받는다.
- **만 14세 미만** — 로그인 전에 만 14세 이상인지 확인한다(체크 상자). 법정대리인 동의 절차는 두지 않았으므로 14세 미만은 로그인하지 못한다.
- **민감정보 공개 가능성** — 리포트 메모는 공개된다. 쓰기 창의 **공용 보드에 올리기**를 끄면 그 글은 이 기기에만 남는다. 방침 11조가 이걸 비공개 방법으로 안내한다.
- **정보통신망법 게시판 의무** — 신고 창구(신고 단추), 불법정보 삭제, 운영자 연락처 표시(방침 14조).
- 수익이 생기면 사업자등록.

## 남아 있는 것

- **관리자 화면** — 지금은 SQL 로 본다. 신고가 하루 몇 건이면 그걸로 충분하고,
  그보다 많아지면 그때 만드는 게 맞다
- **알림** — "우리 동네에 속보" 웹 푸시. 3분마다 조용히 받아오는 것만 있다
- **동네 인증** — 지금은 고르면 그만이라 아무 동네나 고를 수 있다.
  당근마켓식 인증은 위치를 받아야 해서 위 규제 줄을 넘는다
- **탈퇴 후 재가입으로 정지 피하기** — 탈퇴하면 정지 기록도 함께 지워진다. 막으려면
  탈퇴한 카카오 회원번호를 일정 기간 보관해야 하는데, 그러면 처리방침에 그 보관을 적어야 한다.
  도배가 실제로 문제 될 때 정한다
